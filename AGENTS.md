# Project Instructions for Coding Agents

This is the project root for the Belperfi personal-finance lakehouse and report pipeline. Read this file and `README.md` before making project-wide changes. For report behavior, read the canonical prompts under `agent/prompts/`: `personality.system.md`, `ui.system.md`, `financial-settings.md`, and `validator.system.md`.

## Architecture and sources of truth

- Layout: `Scripts/finance/` is the library package (all report, chat, and memory logic; edit it there). Entry scripts live in category folders: `Scripts/apps/finance_app.py` (Gradio UI), `Scripts/reports/` (`weekly_report.py`, `compare_runs.py`, `replay_validator.py`), `Scripts/pipeline/` (`upload_csv.py`, `run_all_issuers.py`, `generate_mock_cd.py`), `Scripts/tools/model_benchmark.py`, and the tests with their fixtures and `testdata/` in the `Scripts/tests/` package. Each entry script that imports `finance` starts with a small bootstrap that puts `Scripts/` on `sys.path` (`Path(__file__).resolve().parents[1]`); project paths (config.json, `agent/`) come only from `finance.settings.PROJECT_ROOT`/`DEFAULT_CONFIG_PATH`, never from `__file__`-relative guesses. There are no top-level compatibility shims; import `finance.*`. `Scripts/local_experiments/` is local-only and ignored by Git.
- `Scripts/reports/weekly_report.py` is the thin email entry point (scheduled task): it loads config and runs agent mode via `finance/report_runner.py` (progress, archive with `_failed` rename, budget/validation/dry-run outcomes, delivery, memory after a send) or legacy mode via `finance/legacy_report.py`; email building/sending is `finance/email_delivery.py`, post-send memory and fact extraction `finance/report_memory.py`, and it re-exports the moved names (tests patch `RUN_ARCHIVE_ROOT` and `send_email` on it). Legacy mode is the working proof of concept: keep its prompt, email, and memory behavior identical. `Scripts/apps/finance_app.py` is the Gradio UI; both generate reports through `finance.reporting.generate_finance_report`. Trace-derived run counts come only from `run_archive.metrics_from_trace`.
- The harness lives in the `finance/harness/` package (`harness.py` runs the loop; `protocol.py`, `prompts.py`, `feedback.py`, `html_safety.py`, `trace.py`, `errors.py`, `transport.py`, `fallback.py`); `finance/agent_harness.py` only re-exports it for existing imports. Instruction text sent to the models belongs in `prompts.py`.
- Author protocol (`finance/harness/protocol.py`, `prompts.py`): the author requests tools with a JSON object `{"tool_calls":[...]}` whose arguments must match each tool's JSON schema (`ToolSpec.parameters`, declared in `reporting.tool_parameter_schemas` and shown in the author's tool list; `trace.validate_tool_arguments` checks them before the tool runs and failures become tool-error evidence; a ToolSpec without a schema shows `"JSON object"`, which keeps the strict golden prompts unchanged) and returns the final report as raw HTML between `<<<REPORT_HTML>>>` and `<<<END_REPORT_HTML>>>`; plain text is derived from the HTML. Never ask the author for `report_html`/`plain_text` JSON. The validator keeps its schema-constrained JSON output.
- Recoverable failures go back to the author instead of aborting: malformed/truncated output gets a format retry; HTML-gate rejections, refused (unknown or over-budget) tool calls, and tool errors become feedback. A model call that times out, cannot connect, returns HTTP 5xx, or is empty is retried once, then the run ends with a fail decision (fallback or last sanitized report, never sent); exhausting `max_agent_rounds` or the `max_run_seconds` run deadline (checked before every model call; each call's timeout is capped at the time remaining, and a timeout caused by that cap is not retried; `run_deadline_exceeded` trace event) ends the run the same way. `max_validation_cycles` is the total number of validator reviews (at most that many minus one revisions; config must give a positive integer, and the harness still treats values below 1 as 1). Revisions get only the top three prioritized errors with the snapshot values they concern (strict guidance; guided sends every error). In a revision the author may dispute a finding the report already satisfies with an optional `<<<REBUTTALS>>>[{"finding": "...", "quote": "<verbatim report text>"}]<<<END_REBUTTALS>>>` block after the end marker; it is stripped from the HTML, malformed blocks are ignored with a trace event, and valid rebuttals go to the next validator prompt for the validator to verify (no Python check of quotes or findings). Repeated identical findings across cycles record an informational `validation_stalled` event. Using the same normalized key, the harness keeps a bounded list (last 10) of earlier error findings absent from the latest cycle's errors and shows it to the author ("ALREADY FIXED IN EARLIER CYCLES (do not reintroduce)") and the validator ("FINDINGS RESOLVED IN EARLIER CYCLES", re-flag only with new verbatim evidence); it is bookkeeping in prompts and the trace (`resolved_findings`), not a filter on findings.
- BigQuery gold-layer data and the deterministic `ReportSnapshot` (`Scripts/finance/report_metrics.py`) are authoritative for current amounts, category groups, monthly totals, MoM values, disposable cash, savings shortfall, top-three discretionary categories, suggested/configured caps, percent of cap, and snapshot bar widths (`savings_shortfall`, `suggested_cap`, `percent_of_cap`, `bar_width_percent`, `top_discretionary_categories`, etc.). Change goal or chart math there (with tests in `test_report_metrics.py`), never in prompts, and keep `ui.system.md` and `validator.system.md` consistent with it; the author copies these fields and the validator verifies and spot-checks them. `finance/report_requirements.py` derives a short month-specific REPORT REQUIREMENTS CHECKLIST from the snapshot (exact headings, bar amounts, Sushi Stack values, goal disclosures, Top 3 rows) that the harness shows once to both the author and the validator; keep its headings in sync with `ui.system.md` (tests in `test_report_requirements.py`). It is prompt content, not a Python check of the report.
- `guidance` (`"strict"` default, or `"guided"`; `model_roles.author.guidance` overrides it; invalid values raise `SettingsError`) changes only how the report is worded, structured, and planned, never the facts: snapshot values stay computed in code and must be exact wherever stated, and the code-computed caps stay in the Top 3 table. Guided mode uses `build_report_requirements(snapshot, "guided")` (required sections and facts in any wording), appends `GUIDED_AUTHOR_ADDENDUM`/`GUIDED_VALIDATOR_ADDENDUM` and the guided checklist instruction (`harness/prompts.py`), allows an optional labeled "Mogumogu's alternative plan" whose arithmetic must reconcile with the snapshot, sends every error finding to revisions with a restructure-allowed instruction, and doubles `max_tool_calls`/`max_calls_per_tool` (`trace.effective_limits`). Strict prompts must stay byte-identical; keep guided text out of strict paths. The effective guidance is recorded in `run_started`, `progress.json`/`run.json` (`collect_run_metadata`), and `metrics.json`.
- Memory, prior reports, and run archives are historical context only. Never reuse their figures as current facts.
- Finance chat (`finance/chat/`, the app's Chat tab) is a declarative analysis spec executed by deterministic pandas code: the model may only fill in an `AnalysisSpec` (`analysis_spec.py`), never write code or see transaction rows; it sees the catalog (`data.build_catalog`), the result `summary` (kept under about 1.5 KB), and the caption. Periods are resolved in Python (`resolve_period`), never by the model; specs pass through `validate_and_repair` (fuzzy matching, chart repairs, notes; `SpecError` lists the closest valid values) before `executor.run_analysis`. Metric math must keep mirroring gold `fact_monthly_spending` (Sale/Return/Adjustment only, `spend = -amount`); change it only with the reconciliation tests in `test_chat_executor.py`. Merchant names come only from `merchants.normalize_merchant` (plus `merchant_aliases`), and every chart label goes through `html.escape` in `charts.py`. `data.load_transactions` takes an injectable BigQuery `client`, caches per project/start for `chat_data_cache_seconds`, and builds the frame from row dicts (no db-dtypes/pyarrow). Chat tests use `Scripts/tests/chat_test_fixtures.py` and fake clients, never BigQuery or a model.
- Finance chat data profile (`finance/chat/profile.py`): `build_data_profile(frame, today=...)` (schema, complete/partial months, latest complete month, data-end lag, transaction types, and a usable/limited/unusable status with a plain-language reason per dimension; thresholds are module constants documented in its docstring and the README table) is built once per load by `data.load_chat_data` next to the catalog. It feeds the DATA PROFILE prompt block (`prompts.profile_block`; no amounts or percentages in it, because the narrative guard only accepts tool-result figures), `validate_and_repair(..., profile=...)` (limited dimensions swapped via `analysis_spec.DIMENSION_ALTERNATIVES`; merchant grouping allowed when the user filters merchants), the executor's auto chart (`LINE_MIN_POINTS`, `HEATMAP_MAX_ROWS`/`HEATMAP_MAX_COLUMNS`, `PIE_MAX_SLICES`), and the Chat tab's example chips (`profile.suggest_examples`, templates and `STATIC_EXAMPLES` in `prompts.py`). Relative periods are anchored to the data's end in `resolve_period` when the data stops before the current month (`month_coverage` defines complete months). Notes the answer must mention are `analysis_spec.Limitation` strings; they reach the model as `summary["limitations"]`, which compaction keeps last. Users see `executor.display_table` (friendly columns, "Aug 2026", weekday names); the model summary uses the raw table.
- Chat engine conventions: the model only routes and narrates through three tools (`chat/tools.py`: `analyze_spending`, `list_values`, `get_month_snapshot`); every tool result sent to a model is a compact JSON payload (at most `tools.MAX_RESULT_BYTES`, about 1.5 KB) and never contains rows, descriptions, or individual dates, and tool errors go back as tool results listing valid values instead of raising. `get_month_snapshot` must reuse `report_metrics.calculate_report_snapshot` (never re-implement report math). Chat instruction text (system prompt, catalog block, tool descriptions, fix/limit notes, user-facing messages) lives only in `chat/prompts.py`. `engine.run_turn` enforces `chat_max_tool_rounds` and `chat_turn_seconds`, runs `check_narrative_numbers` against the tool payloads (one regeneration, then the authoritative-table note), and turns budget refusals, unreachable models, and deadlines into friendly text, never a traceback. Chat model calls use `ModelClient.chat(messages, *, system, tools, json_schema, timeout) -> ChatReply` (provider-neutral messages: user/assistant with `tool_calls`/`tool` results) on the `chat` role (`model_roles.chat`, else `model_name` with `ollama_options["chat"]`); the app builds one guarded client per chat session with `run_id="chat"`. Claude chat turns are append-only: replay the assistant's `provider_content` blocks (thinking, tool_use) unchanged and send tool results as one user message of `tool_result` blocks. The app keeps the DataFrame out of `gr.State` (module cache only), one `ChatSession` per Gradio session hash, `concurrency_limit=1` on the chat event, and never `share=True`. Engine tests use the scripted `FakeChatClient` in `test_chat_engine.py`. The previous spec goes to the model, labeled for follow-ups, only when `session.is_follow_up(text, session)` sees a follow-up cue (whole words such as "now", "same", "also", "only", "instead", "and by", "break that down", "what about", "that", "it", "those", "compare that", "as a ... chart", "switch to"; `session.FOLLOW_UP_CUES`, tests in `test_chat_engine.py`); otherwise it is omitted so a new question starts from defaults; the system prompt carries over its filters/period only for clear refinements ("now only...", "same but...", "break that down by..."), and a new question starts from defaults and says which filters apply.
- The sole configured monthly savings target is numeric `Savings_goal_target` in both `config.json` and `config.example.json`. Do not reintroduce a competing `Savings_goal` setting. Do not reveal or copy runtime secrets from `config.json` into code, prompts, logs, or examples.
- `agent/prompts/*.md` are runtime instructions consumed by the report author and validator. Update them when report behavior or policy changes; do not assume external coding agents automatically load them.

## Report requirements

- Preserve the required report order and content: friendly Mogumogu greeting; Monthly Snapshot with all supplied main category groups and horizontal category bars; Spending Trends & Analysis; Mogumogu's Financial Health Check; four-metric Sushi Stack; Top 3 Discretionary Categories table; and actionable weekly tips with an encouraging sign-off.
- Keep the established cheerful, Japanese-food-inspired Mogumogu personality, including a few appropriate food emoji (not excessive decoration).
- Design for email clients using Material 3-inspired hierarchy and spacing: visible pale blush-pink canvas, light report surface, bright rose/hot-pink/coral accents, dark readable text, restrained surfaces, and consistent spacing. Do not let purple/plum replace pink.
- Snapshot bars use one rose/pink family, one scale across all groups (bar width proportional to spend relative to the largest positive category), and right-aligned amounts sharing a common edge. Label refunds/negative amounts without letting them distort the positive bar scale.
- Keep chart values, table numbers, labels, and trend semantics consistent with the authoritative snapshot. A lower expense is generally favorable and a higher one generally unfavorable; label the direction as well as using color.
- Top-three categories must come from supplied Wants/Discretionary groups, not Needs or fixed/uncontrollable groups. Use configured category goals if present; otherwise follow the savings-target and spending-trend recommendation method in `ui.system.md`. Label advisor-suggested caps distinctly from configured goals; never invent targets.
- Avoid transaction-level or merchant-specific claims (for example, a particular habit or merchant) unless supported by `get_transaction_detail` or `explain_category_change` evidence. `snapshot.notable_changes` (`report_metrics.notable_changes`; thresholds `notable_change_pct`/`notable_change_usd`, top 5 by absolute dollar change) lists the big month-over-month category moves; the author is invited, never required, to call `explain_category_change(category)` (optional `parent_group`, auto-filled from the snapshot and required when a category spans several groups so results match one snapshot row; read-only parameterized SELECT in `bigquery_tools.py`, pure summary in `finance/category_change.py`, result at most about 2 KB and never raw rows) and attribute a change only to what it returns; the validator flags change-driver claims without that evidence. Notable changes are not checklist items. `get_daily_spending`/`get_weekly_spending` (read-only parameterized SELECTs on gold `fact_daily_spending`/`fact_weekly_spending`, report month or predecessor, optional category/parent_group) are the evidence for day, weekday, or week timing claims; edge weeks overlap neighboring months, so weekly totals never reconcile to the monthly total. Gold `fact_monthly_spending` also carries text `month` (month name) and `year` columns; `transaction_month` (a DATE, the month's last day) stays the key every query filters on. With `tool_transport` `"mcp"` (default; `"direct"` calls in-process) the five BigQuery data tools run through the local stdio MCP server `finance/mcp_server.py` (SDK `MCPServer`, i.e. FastMCP) via `finance/mcp_client.McpToolClient`, started lazily and closed when the report ends; keep snapshot restrictions and schemas in `reporting.py`, keep the server a thin read-only wrapper of `bigquery_tools`, and keep MCP tests on `tests/mcp_stub_server.py` or patched `bigquery_tools` (never BigQuery). Do not add chat merchant normalization to it. Tool calls are evidence-driven, not a quota: do not make redundant calls. If a tool fails, its error should be returned to the author with prior context so it can correct/retry or skip it.
- Treat the validator as a skeptical reviewer. It must independently reason through the actual HTML/CSS, math, category eligibility, and goal calculations; missing or unverifiable hard requirements should fail. Its error findings must be evidence-grounded: quote the wrong report text verbatim with the conflicting snapshot field, search for paraphrases before claiming something is missing, and verify author rebuttal quotes instead of repeating a finding unchanged. Use `visual_design` findings for Material 3/design defects and `usability` for readability/accessibility defects. Keep this behavior in the canonical validator prompt, not deterministic Python checks unless specifically requested.

## Change and test workflow

- Inspect the relevant implementation and prompt files before editing; keep changes focused and avoid modifying archived runs unless explicitly requested.
- Do not send email or alter production finance data while validating. Respect `dry_run` in runtime configuration.
- Use the workspace virtual environment `..\.venv\Scripts\python.exe` (it has the Google Cloud packages; the system Python may not). From the project root in PowerShell, run the tests with `& "..\.venv\Scripts\python.exe" -m unittest discover -s Scripts/tests -t Scripts` and the report with `& "..\.venv\Scripts\python.exe" Scripts\reports\weekly_report.py` (the Windows scheduled task "Personal Finance Weekly Report" runs that script with the venv interpreter and the project root as working directory). Tests import `finance.*`, sibling test modules as `tests.<module>`, and entry scripts as `reports.weekly_report`/`pipeline.generate_mock_cd` (the app is loaded from `apps/finance_app.py` by path). The tests mock BigQuery, Ollama, and SMTP; keep them green. Direct dependencies are pinned in `requirements.txt` (`..\.venv\Scripts\python.exe -m pip install -r requirements.txt`); add new direct imports there.
- Console output from `finance/` goes through `finance/log.py` (`get_logger(name)`: one handler on the `finance` logger, `[YYYY-MM-DD HH:MM:SS] message`, written to the current `sys.stdout` with a flush and an encoding fallback); `status_log.log_status` and `ProgressRecorder.log` (as a preformatted line) use it. Do not add `print` diagnostics to library modules; CLI output of `run_compare.main`/`replay.main` and the entry scripts stays `print`.
- Config is read only through `finance/settings.py`: `ReportSettings.from_config(config)` builds a frozen, validated settings object once (limits must be positive integers, `report_mode` known, `memory_schema` safe, `Savings_goal_target` numeric; errors raise `SettingsError`, a `ValueError` naming the key). Defaults live only in `settings.DEFAULTS` (`HarnessLimits` and `model_clients.DEFAULT_TIMEOUT` reference it); the README "Code defaults" table must match it (`test_settings.py` checks). Do not add new `config.get(key, default)` calls; add a field instead. Functions that take `config` accept a dict or `ReportSettings` (`ReportSettings.coerce`). `Gmail_app_credentials` is masked in `repr`; never log settings secrets.
- `model_roles` is the primary model setup: each role (`author`, `validator`, `eval`, `chat`) names `provider` (`ollama` or `anthropic`, for any role), `model`, and its own `options`/`think` (`think` is sent as Ollama's top-level flag, other keys as request `options`). `validator_model_name` and `ollama_options` are legacy fallbacks read only for roles absent from `model_roles`; `model_server_url` (shared Ollama server) and `model_name` (legacy mode, fact extraction, Q&A app) stay.
- Memory is a `finance.memory.MemoryStore(db_path)` object; `open_memory(schema)` returns an initialized store and paths resolve only through `settings.memory_db_path` (`MEMORY_DB_PATH` read at call time). Callers receive a store (duck-typed; tests use fakes). Module-level functions delegate to a default store set by `init_db()` for older callers.
- All model calls go through `finance/model_clients.py`: `ModelClient.generate(prompt, *, system, json_schema, timeout) -> ModelReply` with `OllamaClient` (also embeddings) and `AnthropicClient` (official `anthropic` SDK, imported lazily; credentials only from `ANTHROPIC_API_KEY` or `ant auth login`, never config). Claude roles take `max_tokens` (at most 64000; thinking tokens count toward it), `effort`, `cache_system`, `stream` (default auto: `messages.stream` with `get_final_message()` above 16000 `max_tokens`, same `ModelReply`; the role timeout also bounds the whole stream) and optional `thinking: "adaptive"`. Opus 5.5 / Sonnet 5.5 think by default with depth set by `effort`; never send `thinking: {"type": "disabled"}`, `budget_tokens`, or sampling parameters. Roles are resolved by `resolve_model_role`/`build_model_client(config_or_settings, role)`; `ReportSettings` resolves them once at load. Prompts are built as system (stable instructions, cached for Claude) plus user (per-call content); Ollama must keep receiving the exact concatenated prompt. Use `finance/html_text.html_to_text` for any HTML-to-text need. `finance/ollama.py` and `harness/transport.query_ollama` are compatibility wrappers.
- Every Anthropic call must go through the guarded `AnthropicClient` built by `build_model_client` (or given an explicit `BudgetGuard`); never construct `anthropic.Anthropic(...)` or call `messages.create`/`messages.stream` anywhere else, and never bypass or disable the guard in code. The guard (`finance/budget.py`, prices only in `finance/pricing.py`) checks each request's worst case (prompt chars / 3.5 at list input price plus `max_tokens` output) against `anthropic_daily_budget_usd` (default 15) and `anthropic_run_budget_usd` (default 5) before the call, records every billed call in `agent/runs/cost_ledger.jsonl`, and fails closed when the ledger cannot be read or written. A refusal raises `BudgetExceededError`, which the harness handles like the other run-stop errors (fail decision, never sent, `budget_exceeded` trace event); replay, compare, the app, and the future chat must surface it as a clear message. Pass the report run id (or "replay"/"compare"/"chat") as `run_id`; the chat's `ChatReply` path (`AnthropicClient.chat`) is checked and recorded by the same guard. `test_budget.py` fails if an unguarded SDK call appears outside `model_clients.py`.
- Tests must never make paid API calls (or real Ollama/BigQuery calls): inject fake SDK clients (`AnthropicClient(..., client=fake)`, `build_model_client(..., anthropic_client=fake)`) or a `query=` fake into `ReportHarness`.
- Agent runs stream `progress.json`, `progress.log`, and `trace.jsonl` into `agent/runs/<run_id>/` while they execute (`finance/run_archive.py`); follow one with `Get-Content agent\runs\<run_id>\progress.log -Wait`. `update_index` numbers the rows (newest first), shows local start/end times (progress.json, else the first/last trace.jsonl timestamps, read without loading the whole trace), skips `agent/runs/comparisons/` and `agent/runs/replays/` (`run_archive.NON_RUN_DIRS`), and lists the comparison pages and validator replays saved there. A run without a recorded `anthropic_cost_usd` gets its cost from the Claude ledger (`CostLedger.spend_by_run`, read once per index build; `update_index(root, ledger_path=...)`, callers with settings pass `budget.configured_ledger_path`, else `root/cost_ledger.jsonl`). At run start the email workflow records `collect_run_metadata(settings)` in `progress.json` and `run.json`: `code_version` (short commit and dirty flag; tolerant of missing git), `author_role`/`validator_role` (`settings.public_role`: provider, model, options, think, timeouts; never URLs or secrets), and `harness_limits`.
- `Scripts/reports/compare_runs.py` (logic in `finance/run_compare.py`) sends bounded run summaries to the `eval` role and saves `agent/runs/comparisons/<timestamp>_<n>runs.html` plus `.json` metadata; `--dry-run-prompt` prints the prompt without a model call, and a failed or refused call saves nothing. Run summaries include `code_version`, and the eval prompt tells the model to weigh code-version differences before attributing outcomes to models. Model Markdown is rendered only through `markdown_to_html`, which escapes all text. Tests use fake clients.
- `Scripts/reports/replay_validator.py` (logic in `finance/replay.py`) replays one run's validator `model_call` (chosen cycle, attempt 1) with the configured validator or a `--role-model PROVIDER:MODEL` override, splitting the traced prompt on `prompts.VALIDATOR_REPORT_MARKER` (keep that marker as the start of the validator's user part); `--current-prompt` swaps in today's `validator.system.md`. Results go to `agent/runs/replays/*.json`; it never modifies run folders. `--dry-run-prompt` makes no call. Tests use fake clients and temp run folders.
- Whenever config keys, file structure, or the workflow change, update `README.md` (project structure, runtime config knobs, commands) and `config.example.json` in the same change.
- Never expose credentials, account identifiers, or transaction-level personal details in responses or committed examples.
