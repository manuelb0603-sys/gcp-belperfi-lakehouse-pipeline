Create a polished, consistent HTML email report inspired by Google Material 3 principles: clear hierarchy, purposeful color roles, consistent spacing, readable typography, and restrained surfaces. This must retain Mogumogu's distinctive colorful pink Japanese-inspired identity; do not neutralize it into a generic gray/blue corporate dashboard. This is an email report, not an Android app; do not imitate app controls or depend on modern CSS that email clients commonly strip.

Design system:
- Keep the same section order and visual language across reports. Personalize only small details; do not invent a substantially different layout or palette each time.
- Center a single content column with a maximum width of about 640 px. Give the email page/canvas a clearly visible pale blush-pink background (for example #FFF1F5 or #FFF5F7), with a white or near-white report surface and comfortable inner padding (about 20–24 px where supported). The pink should be visible around the report panel; do not default to a gray or cream-only page. Keep body copy left-aligned and line lengths readable.
- Establish a clear type scale: one report title, distinct section headings, legible body text, quiet labels, and prominent financial values. Use an email-safe sans-serif stack, comfortable line-height, and consistent weights; avoid all-caps labels when they reduce readability.
- Follow a consistent 8 px spacing rhythm. Separate sections clearly, group related details, and use card padding rather than piling on dividers, borders, and shadows.
- Use a visibly pink-forward, cheerful palette: light blush/soft pink surfaces, bright rose/hot pink and coral as the primary brand accents, and dark warm charcoal or berry text for contrast. Avoid purple, violet, and plum as dominant colors. Carry pink through the title or section markers, hero KPI, snapshot bars, and selective table highlights. Keep large backgrounds pale and text dark for readability; never use pale pink for small text on white.
- Keep financial semantics distinct from the brand palette: reserve green/red for favorable/unfavorable spending direction, use muted neutral styling for supporting data, and never use color alone to communicate a trend. A lower expense is generally favorable and a higher expense generally unfavorable; label the direction in words as well.
- Make the latest-month net expense the primary KPI. Follow it with the required four-item "Sushi Stack" comparison: current-month net expense, previous-month net expense, month-over-month change, and disposable cash. Keep these metrics visually grouped as a tidy, scannable vertical stack with a clear primary-vs-secondary hierarchy; do not omit the stack to make the page shorter. Show the disposable-cash formula in a short note. Do not repeat values in other visual treatments.
- Keep category tables compact but comfortable to scan: clear column labels, adequate cell padding, subtle row separators, category names left-aligned, and numeric values consistently aligned. Ensure the content remains usable on narrow screens; use simple HTML tables and inline styles when needed for email compatibility.
- Use rounded corners sparingly and avoid repeated heavy shadows, nested cards, thick outlines, decorative separators, and emoji on every heading. Preserve the Mogumogu identity with at most a small, intentional playful accent.
- Maintain strong text/background contrast (at least WCAG AA where practical), meaningful heading structure, descriptive table headers, and readable content when color or decorative styling is unavailable.

3. Spending Trends & Analysis: explain the most meaningful current-versus-previous-month changes in clear, friendly language. Explain increases/decreases as spending direction, not as inherently good/bad without context. The snapshot lists notable_changes (the largest month-over-month category moves, largest dollar change first). Investigate spending spikes before writing this section: a spike is a notable_changes entry with direction "increase". For each spike, starting with the largest, call explain_category_change(category) with the entry's parent_group to find what drove it (more transactions, larger purchases, specific large transactions, or new descriptions), and call get_daily_spending or get_weekly_spending with that category when knowing when the extra spending happened (one large day, a busy week, or spread across the month) makes the explanation clearer. Then name each spike with its snapshot change and its driver, and when total net expense rose month over month, say which spikes account for most of the rise. Attribute causes only to evidence the tools return. If a tool fails, the evidence is inconclusive, or the tool budget runs out before every spike is investigated, say plainly that the spike is not yet explained instead of guessing. Do not repeat a call that already returned the evidence. You may call explain_category_change for notable decreases too, but spikes come first. Never invent habits or merchants. Weekly totals overlap neighboring months and must not be presented as adding up to the monthly total.

5. The Sushi Stack: show all four metrics—current-month total net expense, previous-month total net expense, MoM percent change, and disposable cash—in a visibly grouped vertical comparison stack. Use the exact snapshot values and months; explain disposable cash as monthly deposit minus (current net expense plus fixed costs). A negative result is valid and must remain negative.

Goal-setting method used to produce those fields (for explanation only; be explicit that these are planning suggestions, not guaranteed outcomes):
- Treat snapshot.savings_goal (derived only from the configured Savings_goal_target) as the authoritative monthly savings target. First calculate current projected savings as disposable_cash = monthly_deposit - (latest_total_net_expense + fixed_costs).
- If projected savings are below the target, calculate the shortfall = target - projected_savings. Sum current spending across all categories whose supplied parent_group identifies them as discretionary/Wants. If this total is positive, propose category caps for discretionary categories by allocating the shortfall proportionally to current spend: category_cut = min(current_category_spend, shortfall * current_category_spend / total_current_discretionary_spend); suggested_cap = max(0, current_category_spend - category_cut). Apply the calculation consistently, including categories outside the displayed top three, so the displayed three are not falsely represented as the whole plan. If the shortfall exceeds total discretionary spending, cap these categories at zero and state that the savings target cannot be reached through discretionary cuts alone.
- If projected savings already meet the target, use trends to set maintainable caps: for a category whose spending increased, use the previous-month amount as a suggested cap when available; otherwise use current spending as a maintenance cap. If spending decreased, use current spending as the maintenance cap rather than encouraging a rebound.
- Percent of goal = current category spend / suggested or configured category cap * 100, only when the cap is greater than zero. Label a suggested cap distinctly from a user-configured goal, explain the shortfall/trend basis briefly, and do not call a recommendation a guaranteed savings result. If no numeric savings target or adequate discretionary category evidence exists, state that fact and avoid fabricating a dollar goal.
